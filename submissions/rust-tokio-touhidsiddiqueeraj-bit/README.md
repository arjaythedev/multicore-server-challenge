# Rust / Tokio — touhidsiddiqueeraj-bit

Front: direct

Rust 1.99.0, Tokio 1.53.2, tokio-postgres 0.7.18, PostgreSQL 18 and mimalloc 0.1.52. Dependencies are pinned in Cargo.lock.

The architecture builds on [Scooter1337's MIT-licensed rust-tokio submission](https://github.com/arjaythedev/multicore-server-challenge), which itself builds on cknutson12's MIT-licensed rust-hyper submission; attribution is retained in LICENSE. This submission keeps that architecture and extends it in three areas described below.

- Direct HTTP/1.1 using httparse, with fixed-capacity buffer free lists, separate 1 KiB request buffers, stack response headers and vectored writes. Buffers are released while sockets are idle. Active request futures are boxed so idle connections retain a small task. Read completion is bounded after the first request byte; idle keep-alive remains unlimited.
- Prepared generic plans, separate read/write connections, and one statement per mutation. Failed connections and their statements are replaced together, without replaying requests. Global and tag pages compute exact favorite counts and viewer membership in one index scan. Article metadata is computed after pagination; API-bounded pages improve generic-plan cardinality, capped tag counts avoid aggregation when the cap is proven, and favorited-page membership is computed once per request. Existing tags are read without unnecessary updates or locks.
- Compatible read queries prefer connections with matching in-flight queries within a bounded distance of the least-loaded connection, with rotating ties and no collection delay. Read actors combine compatible queued reads into one array-parameterized LATERAL query and route rows back by request ordinal. Overlapping global, tag, author and favorited pages share article metadata enrichment within that SQL execution; viewer flags remain per request. **Concurrent requests for the same article now share one execution too: single-article reads resolve each distinct slug's metadata (tags, favorite count, author) once per drain batch, and comment-list requests read each distinct slug's comment page once, with both still computing their viewer membership per request inside the same SQL execution.** Counts are materialized before joining pages. Batches without enough matching page/filter arguments and personal feeds keep the original query. Other reads keep packed Bind/Execute messages with one Sync. Groups contain at most 32 requests with no collection delay; each SQL execution takes a READ COMMITTED snapshot and results wait for ReadyForQuery. No returned data is retained across requests. The vendored tokio-postgres changes drain errors before reuse and preserve upstream licenses.
- Durable group commit: connection-owning actors collect concurrent writes, commit, then release responses. Failed batches roll back and retry requests individually; uncertain commits are never retried. **Favorites, unfavorites and article updates answer from the mutating statement itself instead of re-reading after commit: the statement's own snapshot cannot see its CTE's changes, so the favorites count is adjusted by the number of changed rows (zero on a no-op), the post-favorite `favorited` flag is a known constant, and article-update authorship is still enforced against the pre-update lookup. The response is released only after the implicit transaction commits. Concurrent comment pages join the read drain.**
- Borrowed PostgreSQL text arrays, direct JSON serialization and SSE2 string escaping on x86-64. Fat LTO and one codegen unit.
- Bounded bcrypt work using the Openwall/libxcrypt 4.4.36 core, with fresh random salts and cost 10. Up to four independent hashes are interleaved to hide dependent table-load latency, retaining every bcrypt round. Startup checks compare the interleaved paths against the original core. Embedded NULs use the portable Rust backend.

Every request reads PostgreSQL. Authentication checks signatures and expiry on every use; there are no result, token-verification or password caches. No schema/config changes, CPU affinity or host tuning.

On eight CPUs the defaults are two Tokio workers, six read connections, two grouped write connections and one bcrypt worker. A write group waits up to 1 ms and contains at most 128 requests. Bcrypt collects up to four jobs with a 160 ms collection window. Optional process settings: `APP_THREADS`, `DB_CONNS`, `DB_WRITE_CONNS`, `BCRYPT_THREADS`, `WRITE_BATCH_US`, `BCRYPT_BATCH_MS`, `READ_BATCH_SIZE` (default 32; 0 disables read batching), `READ_BATCH_US` (default 0), `READ_SQL_BATCH` (default 1; 0 keeps individual SQL executions), `READ_ROUTE_SLACK` (default 8; 0 limits affinity to equal loads, `off` keeps ordinary least-loaded routing), `READ_TAG_ROUTE` (default 1), `READ_TAG_BATCH` (default 1), `READ_COMMENT_SET` (default 1; comments then read the viewer's followee set once per execution).

The API and initial SQL build on [cknutson12's MIT-licensed rust-hyper submission](https://github.com/arjaythedev/multicore-server-challenge/pull/1), with attribution retained in LICENSE. The native bcrypt source and its license are documented in native/README.md.

Local validation on a 4-core desktop with PostgreSQL 18 in a container and the full 500,000-article seed: all 197 conformance checks pass on the dev seed, the release unit tests pass, a 60-second loadgen run at 12,000 users on the full seed reports a zero-error PASS verdict, and a 40-worker same-slug read storm (2,000 concurrent single-article/comment requests over 10 articles plus interleaved favorite writes) reproduced every reference response byte-for-byte while the shared executions were active. Per-statement generic-plan timings on the full seed show the folded favorite response at ~70% of the cost of the previous two-statement flow, and the folded article update at a similar ratio.

The saturated-load A/B comparisons on the same box were inconclusive (localhost load from unrelated processes moved per-run CPU by more than the measured effect at 12,000 users), so no end-to-end claim is made here; the submitted changes are correctness-verified everywhere the harness can reach, stay within the challenge rules (≤95 connections, no caching, committed writes), and remove one round trip and statement per write plus one duplicate read per concurrent same-article execution.
