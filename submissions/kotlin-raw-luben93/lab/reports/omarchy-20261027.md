# Lab report 2026-10-27/28: surviving the overload probe, batch-shared reads, and the 120k cap

**Update 2026-10-28: the scorer's search reaches its cap.** Two more changes, now the defaults: favorited/following
looked up once per viewer in the shared lists (`READ_VIEWER_FLAGS`), and 8 read + 4 write Postgres connections
(were 6 + 2). The scorer's own search passed its 144,000-user probe and its 5-minute hold here: 37,413 req/s, p95
240 ms, p99 489 ms, 0.06% errors. **~120,000 box-equivalent: the cap, #1's score.** The same build with the previous
defaults held only 92,000 in the same session: its 2 write connections back up under load and the writes' latency
breaks p99 (sections 5.4-5.5). A confirmation run of the exact package with no server settings, hours later, held
**140,000 (~117k box)**: its 144k probe failed on p95 alone after one backlog burst. 144k is the edge of this
machine's CPU, not a margin (section 5.6).

Box simulation on an i7-13700H laptop: server + Postgres 18 on CPUs 0-7 (4 P-cores + their HT siblings, like the box's
8 vCPUs; Postgres in a container with `--cpuset-cpus 0-7 --memory 16g` and the box's pg-conf values for 8 cores /
16 GB), the challenge's own load generator on CPUs 8-19, full seed, JDK 27. Searches use the scorer's own `loadgen
search`, with its start and cap scaled x1.2 (13,200 / 144,000), this machine's speed relative to the box (the Oct 24
lab's rust-tokio calibration; consistent with this build: 120k here, 100k on the box). **Box estimate = local / 1.2.**

## TL;DR

**Why the official score swung from 100k to 88k.** The scorer always overloads us once: doubling from 11k reaches its
120k cap, which is past our capacity, and it never restarts the server afterwards. In that overload the 1 GB heap
filled up (every queued request held an 8 KB response buffer from the moment it was parsed), and `OutOfMemoryError`
hit the catch blocks of the HTTP loops, Postgres workers and the bcrypt thread, which then died for good. Which threads
died decided the score: none (100k), one of six Postgres read workers (88k; the hold's Postgres CPU fits exactly one
lost connection). Reproduced here: at the 144k probe the merged build died completely (every app thread gone, heap
full, 143k sockets left open) and answered nothing afterwards.

**Why this version will be faster.**
1. *It survives the overload.* Threads catch everything without allocating, response buffers are taken only when the
   response is written (~0.5 KB per queued request instead of ~8.8 KB), the heap is 3 GB, and queued work whose
   client has already given up is dropped before it reaches Postgres. Overload-then-recover test: after the 144k
   overload the server passes 105.6k again and holds it for 5 minutes (the merged build: 100% errors). So the
   score no longer depends on luck: 100k (box) becomes the floor, not the best case.
2. *Postgres does ~25% less work per request.* Our app was already as cheap as #1's (71 vs 74 us/request on the box);
   Postgres was not (253 vs 159). Like #1, each batched statement now computes every distinct count, page and
   article once and joins it back to each request (same columns, same JSON), and a 20 ms gather window makes batches
   big enough to share. At 120k users here: Postgres 170 -> 127 us/request, app 46 -> 40, box CPUs 91% -> 75% busy at
   the same load. The global list alone went from 127 s to 44 s of Postgres time per 2 minutes.
3. *The writes no longer set p99, and Postgres gets its idle cores.* The 2 write connections were ~100% busy at 120k
   (group commits wait on the WAL flush; ~1.9 backends in `WalSync`/`WALWrite` at any time), and a burst made the
   write queue explode (one run: 6,375 queued, 4.6 s waits). The 6 read connections queued while Postgres had idle
   cores. 4 write and 8 read connections fixed both (120k profile: p99 5,861 -> 143 ms).
4. *favorited/following once per viewer* in the shared lists (`= ANY` scans instead of two probes per row): global
   list 6.3 -> 3.2 ms per 60 requests, author list 7.6 -> 3.8, tag list 12.9 -> 10.7; Postgres 126 -> 118 us/request.
5. Result: the scorer's search holds **144,000 here, its cap (~120k box)**. Without items 3-4: 130,000 (2026-10-27)
   and 92,000 (2026-10-28, same session as the 144k): the old defaults were also the less stable ones.

**What more we can optimize (ranked by evidence).**
1. ~~Writes~~ and 2. ~~read connections~~: done (8 + 4), see above.
3. **Feed: 45% of Postgres time** for 8% of requests (~0.7 ms each under load). Per viewer, so nothing to share:
   ~37% of it is the capped count (it walks ~890 index entries per request), ~36% the per-followee fan-out. A single
   pass that counts and picks the page from the same followee scans could save a third of it.
4. **Comments: 15%, unchanged by sharing.** Each request still gets its own copy of every comment row. Send each
   distinct thread once and fan it out in the app (like the tags broadcast, keyed by slug), and compute `following`
   from each viewer's followee set.
5. ~~favorited/following per viewer~~: done. Next in line after feed and comments: a **40 ms gather window** (120k
   profile: Postgres 128 -> 116 us/request, p95 76 -> 118 ms; not yet run through the search).
6. The app is not the limit (1.4 of 8 cores at 120k; 37% of its CPU is the `send` syscall, 15% JSON escaping).
   **Native is not faster:** the merged Kotlin/Native build held the same 120k here, at 59 us/request of app CPU vs
   40-46 for the JVM, with the same Postgres cost.

### 5.5 Why the previous defaults scored 130k one day and 92k the next

Same code, same machine: the failures were all on p99 with p95 under 100 ms. The slowest 1% of requests are writes
waiting for one of only two write connections, each held ~60-85 ms per group commit by this disk's WAL flush; how
bursty the session was decided whether p99 crossed 1 s. With four write connections that queue no longer forms.

### 5.6 The cap is the edge: CPU-bound at 144k, and p95 is now the gate that fails

At 140-144k users the box CPUs are 97-98% busy (Postgres ~5.9 cores, the app ~1.9, everything else ~0.15) and
throughput stops growing: 36,155-37,599 req/s across runs (the 01:00 run was ~4% faster than the 09:00 one). The
load is a closed loop (each user thinks ~7 s per page), so past that plateau extra users simply wait: at 144k and
36.2k req/s, Little's law puts the mean response time near 190 ms. That alone would pass (p95 < 500 ms) if the
waiting were spread evenly. It isn't: in the confirmation run's 144k probe one burst right after the ramp queued
17,838 reads (all 8 read connections busy, feed batches of ~200 viewers taking 300-450 ms), and it took ~30 s to
drain with ~3% spare CPU, so everyone queued behind it and p95 reached 665 ms while p99 stayed under 1 s. The
night run's 144k probe had no such burst (p95 217 ms).

What would add margin: cheaper requests (the feed is 46% of Postgres time at 8% of requests); and a queue
discipline that keeps fresh requests fast during a burst instead of first-come-first-served for all.

## What changed

- Overload: `util/Log.kt` (`logSafe`), lazy response buffers (`http/Exchange.kt`, `Engine.kt`), guarded worker and
  loop catch paths (`db/Worker.kt`, `jvmMain/.../EpollHttp.kt`), abandoned reads and bcrypt jobs dropped (`Ex` is its
  coroutine's context element; `db/Reads.kt`, `auth/Auth.kt`), queue caps with 503 (`App.handle`), `start.sh` heap
  3 GB with 4 MB regions. `OVERLOAD_GUARD=0` turns off dropping and caps.
- Shared reads (`READ_SHARE`, default 1): `app/Sql.kt` `ReadShare` shapes; `READ_GATHER_MS` (default 20) and
  `READ_MAX_BATCH` (default 256) in `db/Reads.kt` (+ `db-gather` clock thread). `READ_SHARE=0 READ_GATHER_MS=0`
  restores the previous behaviour exactly.
- Per-viewer favorited/following in the shared lists (`READ_VIEWER_FLAGS`, default 1; `app/Sql.kt`
  `viewerFlagsList`), and Postgres connections 8 read + 4 write by default (`Main.kt`: one per CPU, one per two).
- Instrumentation: with `DB_STATS_S`, one line per interval with each read kind's requests/batches, queue wait and
  round trip, read/write connection utilization, write and bcrypt waits (`util/Timing.kt`); `SQL_PRINT=1` prints the
  read statements and exits.
- Conformance 197/197 with shared reads and per-viewer flags, and with `READ_SHARE=0 READ_GATHER_MS=0`; 167/167 JVM
  unit tests. The optional Kotlin/Native target (`CONDUIT_NATIVE=1`) was not rebuilt in the lab.

## Caveats

- Local numbers, not the box: the x1.2 factor comes from one calibration and this build's own 120k/100k agreement.
  The box's network (a real NIC, remote load generators) and disk (WAL flush time) differ.
- Background load on this laptop: CPUs 0-7 had ~1.2 cores busy with other host work when idle (~0.5 under load).
- Rules: sharing reads within one execution among requests that were all waiting when it was sent, with nothing kept
  afterwards, is the #1 entry's reading of rule 5 (and our tags broadcast's). `READ_SHARE=0` keeps the stricter one.
