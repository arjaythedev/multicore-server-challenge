Built with JDK 27 (Gradle only) and Kotlin/Native 2.4.21 in 1m43s. 1.7 MB `conduit.kexe`, only "redundant conversion"
warnings. Conformance: RESULT: PASS (197/197) on conduit_dev and on conduit_seed.

| users | pass | req/s | p50 | p95 | p99 | app µs | PG µs | total µs | app CPU | RSS |
|--:|---|--:|--:|--:|--:|--:|--:|--:|--:|--:|
| 32000 | yes | 8482 | 0.2 | 15.4 | 33.5 | 278 | 162 | 439 | 236% | 59 MB |
| 64000 | yes | 16953 | 0.3 | 14.2 | 41.4 | 165 | 183 | 347 | 279% | 92 MB |
| 90000 | yes | 23844 | 1.4 | 16.1 | 50.1 | 134 | 174 | 308 | 320% | 128 MB |
| 120000 | **no** (p95 519) | 29192 | 351.0 | 519.2 | 576.5 | 107 | 156 | 263 | 313% | 1465 MB |

kraw-jvm passed 120k (p95 22-32 ms) where native fails. Native app CPU barely grows with load (236% -> 279% -> 320% ->
313% while req/s goes 8.5k -> 29k), and per-thread sampling (`/proc/<pid>/task/*/stat`, 10 s windows, 64k run) shows
**two threads at ~100% each, all the time (~37% user / ~63% kernel)**, with every other thread at 0-3%. They're at 0%
during low-load warm-up (~9%). At 32k they already burn ~2 cores for 8.5k req/s, where the JVM build needs ~0.44 cores
for all app work. That looks like two **spinning** event loops, not saturated ones.

**Suspected cause: NativeHttp.kt:171 drains the wake eventfd with `recv(wakeFd, …)`.** recv(2) on a non-socket fails
with ENOTSOCK, so the eventfd counter is never reset. After the first cross-thread post that writes the eventfd
(posts happen under load, e.g. a DB thread handing a partially written response back for EPOLLOUT), the level-triggered
wakeFd stays readable forever, so `epoll_wait` returns immediately on every pass: 100% CPU per loop, mostly kernel.
That costs 2 of the box's 8 cores, which explains the 120k failure (app 313% + PG 455% ≈ 96% of the box).
Fix: `wakeFd -> platform.posix.read(wakeFd, wakeBuf.addressOf(0), 8u)`.
Confirmed at light load in the official search's 8k probe (2.1k req/s): native app CPU **208% of one core** vs kraw-jvm
**10%**, with Postgres equal (3.4% vs 3.1% of the box).
A few sequential curls don't trigger the post path (both builds idle at 0%), so the check is an A/B at 120k with
server idle CPU measured 20-30 s after the load ends (below). Native HTTP_THREADS=3/4 at 120k is also queued: if the
loops spin, more loops burn more cores. No perf/strace on this host (no root), so no syscall breakdown.

### Finding: kraw-jvm stops serving entirely under overload

At 160k, the per-second loadgen timeline shows normal overload up to ~140k connections (completions plateau ~31k/s,
p95 rising to 1.4 s). Then, at the end of the ramp, **completions drop to 0 and stay there**: every request after that

0 errors).

Why it matters: the scorer never restarts the server and doesn't reset between phases. If the wedge is permanent, the
first failing probe takes down every later bisect probe and hold, and the run ends with no passing hold.
Being reproduced (below) with jstack dumps during the stall and a recovery check after the load stops.

## D. kraw-jvm overload wedge: reproduced, root cause = heap OOM kills the event-loop threads

Repro (f4d115e, defaults, -Xmx1g): 160k users, 60 s ramp + 40 s, then 30 s idle, then 2000 users for 20 s.

- Timeline: overloaded but serving for ~25 s after the ramp (~35k req/s started/s, p95 750-970 ms). Then at
  t≈85 s completions collapse to ~0 and everything times out.
- **Permanent**: 30 s after the load stopped the JVM is at 0% CPU, `curl /api/tags` times out (5 s), and the
  2000-user follow-up run gets **100% errors** (all 10 s timeouts).
- jstack before the collapse: `http-0 http-1 pg-read-0..5 pg-write-0..1 bcrypt-0`. After: **`pg-read-2 pg-read-5
  pg-write-0 pg-write-1 bcrypt-0`**. Both HTTP loops and 4 of 6 read workers are gone.
- server.log:
  ```
  db: read continuation threw: java.lang.OutOfMemoryError: Java heap space
  db: write continuation threw: java.lang.OutOfMemoryError: Java heap space
  http: handler failed: java.lang.OutOfMemoryError: Java heap space
  http-1: loop error: java.lang.OutOfMemoryError: Java heap space
  http-0: loop error: java.lang.OutOfMemoryError: Java heap space
  http: engine error, closing connection: java.lang.OutOfMemoryError: Java heap space
  Exception: java.lang.OutOfMemoryError thrown from the UncaughtExceptionHandler in thread "http-0"
  Exception: java.lang.OutOfMemoryError thrown from the UncaughtExceptionHandler in thread "pg-read-3"
  ... (pg-read-1, http-1, pg-read-4, pg-read-0)
  ```

So under sustained overload the 1 GB heap fills (per-connection buffers plus requests/responses queued without a
bound), the OOM kills the loop and worker threads, and the process lives on with nothing serving. Under the scorer
(no restart, no reset between phases) the first overload probe would turn every later probe and hold into a failure.
Native shows the same unbounded growth (RSS 128 MB at 90k -> 1465 MB at 120k) but has no heap cap to hit.

Suggestions (in rough order):
1. Bound the work in flight: cap queued DB requests and per-connection buffered bytes; when over the cap, stop
   reading from sockets (backpressure) or answer 503 quickly, instead of buffering.
2. More heap: the box has 16 GB and Postgres takes ~4-5 GB. At 128k (passing) the heap was fine; something like
   -Xmx3g plus a bound from (1) gives headroom.
3. A thread that dies must not leave a zombie: catch Throwable in the loops and keep going, or exit the process
   (`-XX:+ExitOnOutOfMemoryError`) so failure is at least visible. (A crash also isn't restarted on the box, so
   (1) is the real fix.)

**Why this is urgent for the real score:** the scorer's `loadgen search` default is `-max 120000`, so its doubling
goes 64k -> 120k. The box is ~1.2x slower than this machine, so a 120k probe there corresponds to ~144k here: past
kraw-jvm's saturation, between 128k (fine) and 160k (wedged). Here the wedge followed ~25-50 s of sustained overload,
and a probe is 60 s ramp + 60 s measured. As it stands, the 120k probe on the box is likely to OOM-wedge the server,
and every bisect probe and hold after it would fail.

**Confirmed: the original native server spins two cores forever once its wake eventfd has been written** (199% CPU

(p95 24 ms vs 22-32 / 31.7 ms), with 215 MB RSS vs JVM 1.1 GB. Patch:

```diff
-                    wakeFd -> recv(wakeFd, wakeBuf.addressOf(0), 8u, 0)
+                    wakeFd -> platform.posix.read(wakeFd, wakeBuf.addressOf(0), 8u)
```

### Artificial per-process `RLIMIT_NOFILE` tests

These are idle keepalive connection-cap tests, not scored HTTP pressure holds. The JVM at soft/hard limit 65,536
held 65,512 of 70,000 offered connections; at limit 200,000 it held 199,976 of 200,000. The fixed Native temporary
candidate at limit 65,536 held 65,519 of 70,000. In each case the process reached its FD limit and logged `EMFILE`
accept pauses; already established idle connections remained usable for a second request after 30 seconds. Failed
connections timed out at the load client's deadline. Artifacts are under `/tmp/mcsc-highpressure-20261024/fdtests/`.

This confirms a single process cannot serve 200k connections with a 64k nofile limit. Raising the service limit is
the direct fix where permitted. Multiple `SO_REUSEPORT` processes can multiply per-process FD capacity if each owns
its connections, but do not bypass global socket/file limits and can worsen the measured PostgreSQL bottleneck if
they multiply DB pools. No multiprocess run was performed.

### Tuning interpretation

At the matched 128k holds, PostgreSQL used roughly 5.5 cores while the application used 1.5-1.9 cores. Database work
is the largest measured CPU consumer; prioritize the unmeasured `tune-pg` query/batching work and preserve the tested
pool settings before adding application concurrency. The Native eventfd change remains a compelling isolated fix,
but a 200k Native idle-cap run and a scored Native revalidation are still pending Copilot's next benchmark pass.

One earlier Native 128k attempt is excluded from comparison: its three-target fanout exhausted local ephemeral ports
(`no_local_port` errors and loadgen limitation). The corrected fanout is used for the results above.
