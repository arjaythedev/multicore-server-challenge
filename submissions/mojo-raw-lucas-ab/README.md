# Mojo, no framework, no C

Front: direct

Work in progress. Everything is Mojo 1.2.0, with no `external_call` / FFI into C: Linux syscalls are raw `syscall`
(x86_64) / `svc #0` (aarch64) instructions through Mojo's inline assembly, and the HTTP server, the Postgres wire
protocol client (SCRAM-SHA-256 login, prepared statements, pipelining), SHA-256, HMAC, PBKDF2 and base64 are written
in Mojo.

All 19 endpoints are implemented with SPEC.md's reference SQL and pass the conformance suite (197/197); the
normalized transcript is identical to `bench/cmd/conformance/golden-dev.jsonl`. No performance work on the SQL yet.

- `src/main.mojo`: forks `WORKERS` event-loop processes and `BCRYPT_WORKERS` bcrypt processes (raw `clone`) and
  supervises them.
- `src/server.mojo`: per-worker transport: `SO_REUSEPORT` listener, connection table, Postgres and bcrypt sockets.
- `src/app.mojo`: the epoll event loop. A request is a chain of steps (Postgres batches, bcrypt jobs) on its
  connection; `src/api.mojo` has routing and every endpoint's steps, `src/reqs.mojo` the shared parsing/rendering.
- `src/pg.mojo`: the Postgres client. `src/sql.mojo`: the prepared statements.
- `src/bcrypt.mojo`: bcrypt (OpenBSD's algorithm; `src/blowfish_pi.mojo` is generated by
  `tools/gen_blowfish_pi.py`, which computes pi's digits). `src/bcrypt_worker.mojo`: bcrypt runs in separate worker
  processes, reached over `SOCK_SEQPACKET` socketpairs, so a ~60 ms hash never blocks an event loop.
- `src/jwt.mojo`: HS256 sign/verify, every request. `src/jsonin.mojo`: a strict JSON tokenizer for request bodies.
- `src/http.mojo`, `src/json.mojo`, `src/crypto.mojo`, `src/linux.mojo`, `src/buf.mojo`.

Toolchain: `install.sh` installs Mojo 1.2.0's compiler from PyPI (Modular's official wheels, `mojo-compiler` and
`mojo-compiler-mojo-libs`), pinned by version and SHA-256 in `mojo-requirements.txt`, into a venv at `/opt/mojo`;
`build.sh` uses it. The binary links Mojo's runtime libraries from there. Checked on a clean `ubuntu:24.04` (x86_64)
through `tools/run_submission.sh`, which runs any submission the way the box does: 197/197.

Settings: `WORKERS` (default 2), Postgres connections per worker `PG_READ_CONNS` (default 6) and `PG_WRITE_CONNS` (default 2), `BCRYPT_WORKERS` (default 2),
`PG_GENERIC_PLANS` (default 1), `PG_GROUP_STATS=N` (log commit-group counters every N groups).

## Optimizations

- **Session `jit = off` and `plan_cache_mode = force_generic_plan`** (sent in the startup message; session-level,
  rule 2). A generic plan can't know `LIMIT $2` is at most 100, so it costs the list queries at ~50k rows, above
  `jit_above_cost`: each execution would JIT-compile for ~136 ms, so `plan_cache_mode = auto` re-plans them on
  every call instead (~0.25 ms, as much as executing them). With JIT off the generic plans run as fast as custom
  ones. Full seed, 15k users, 5 interleaved A/B rounds (`tools/ab.sh`): planning 154 → 2 ms per second, statement
  time −18%, Postgres CPU per request −14% (−10% without the noisiest round), lower in every round.

- **Each list is one statement: the page's ids first, then the per-article subqueries for those rows only, with
  the capped count in the same statement** (`sql.list_statement`). The ids are cut with `OFFSET $3 LIMIT 100` (a
  constant, so the generic plan estimates ≤100 rows; `limit` is validated to 1..100, so the rows are the same) and
  then `LIMIT $2`. The reference global and author pages ran the subqueries for the rows OFFSET skips too.
  `tools/diff_lists.py`: 400 random cases identical to SPEC.md's SQL (rows, columns, counts). 5 interleaved A/B
  rounds: Postgres CPU per request −3.9% (lower or equal in every round); per list request, global −22%,
  favorited −6%, feed unchanged, tag and author +4% (within noise). The tag, favorited and feed reference queries
  already picked their ids first.

- **Tag names by primary key** (`sql.TAG_LIST`): `ARRAY(SELECT (SELECT t.name FROM tags t WHERE t.id =
  at.tag_id) FROM article_tags at WHERE at.article_id = a.id ORDER BY 1)` instead of the reference join, whose
  generic plan seq-scans and hashes all 200 tags for every article. `tools/diff_lists.py`: 480 cases (lists and
  single articles) identical. 5 interleaved A/B rounds (one discarded: the baseline stalled): Postgres CPU per
  request −7 to −10%; per call, global list −23% and tag list −15% in every round, the others within the ±6%
  that unchanged statements moved.

- **Separate read and write connections** (`PG_READ_CONNS` 6 and `PG_WRITE_CONNS` 2 per worker; `pg_read()` /
  `pg_write()`). A batch waits for every batch pipelined before it on its connection, so with shared connections a
  commit that stalls (a slow WAL flush, a lock) held up every read queued behind it. Every batch with an INSERT,
  UPDATE or DELETE goes to a write connection; the lookups before writes, and the re-reads after them, are reads.
  `tools/stall_test.sh` (writes to `favorites` locked 3 s in every 10, ~4k req/s): read p95 2.3 s → 0.3 ms
  (max 7 ms); overall p95 1.9 s → 1.3 ms. Writes still wait for the lock, as they must.

- **Group commit on the write connections** (`PgConn.begin_member` / `close_group`, `app.on_group`). A write
  connection has one batch in flight; requests that arrive meanwhile wait and then go out together, all their
  statements before one Sync, so one implicit transaction and one WAL flush commit them (at most 128). A slow
  flush makes the next group bigger instead of growing a queue of commits. Each response is still sent only after
  its commit (rule 6). If any statement in a group fails, the whole transaction has rolled back, so each member is
  resent alone and gets the result it would have had by itself; a lost connection ends the server, so an uncertain
  commit is never retried. `tests/group_commit_check.py`: 60 registrations with duplicate usernames, piled up behind
  a lock into groups that fail and are retried member by member: one 201 per username, the rest 422.
