# go-rr-sirkostya009

Front: direct

Go 1.27.2, no net/http server. Routing is generated by [rr](https://github.com/sirkostya009/rr), JSON by
[ggen](https://github.com/sirkostya009/ggen), Postgres through [pgx](https://github.com/jackc/pgx) v5.11.0.

## HTTP

- One epoll loop per core, each with its own `SO_REUSEPORT` listener. An idle keep-alive connection is a
  small struct in a table indexed by fd: no goroutine, no buffer.
- Requests are parsed in place. Only the method, target, `Authorization`, `Content-Length` and `Connection`
  are read. Once the head is in, the target and `Authorization` are copied into a pooled `*http.Request`, which
  is handed to rr's generated `ServeHTTP` on its own goroutine. One request per connection is served at a time,
  so pipelined requests keep their order.
- Bodies are not buffered by the server. ggen's stream reads first what came with the head, then the rest
  straight off the socket into its own buffer. A request with a body keeps the 4 KB buffer its head came in
  only until that part is read, then the buffer goes back to a pool. A body needs a `Content-Length`: a
  request with a `Transfer-Encoding` gets `411 Length Required`.
- Responses are not buffered either. The single `Write` from ggen's encoder sends the head and ggen's buffer in
  one `writev`. Only what the socket does not take is copied, and sent when it is writable again.

## Reads

Postgres is the bottleneck, so most of the work goes into spending less of it per request.

Every article, comments, list and feed read of a batch is answered by **one execution of one statement**
([`reads.go`](reads.go)), with the requests passed as arrays (`unnest(...) WITH ORDINALITY`):

- Each read gets its page as an array of article ids, and which of them its viewer favorited from one
  `user_id = v AND article_id = ANY(page)` scan.
- Each distinct article on any page is read once: author, favorite count and tag ids, with the body only
  when an article read wants it. Tag names come from one read of `tags` ranked by name, so tag lists keep the
  database's order.
- Counts are deduplicated per tag, author or user before they are sent. `following` comes from each viewer's
  followee list.
- Feeds share the followees several of the batch's feeds follow: their capped article counts are counted once,
  and the (limit+offset)-th newest article of each is a floor for the pages of the feeds that follow them, so
  a feed's page is one index scan over its followees that stops at the floor.

Reads run on two lanes. The cheap lookups (tags, current user, login, profile) go to two connections that take
whatever is queued when they free up. The statement above runs on eight connections, its batches starting at
least 10 ms apart, so they grow with the load and share more. Under heavy load every worker is busy and
batches grow on their own, up to 1536 reads: two batches merged into one cost Postgres about 15% less, but a
bigger one holds its reads too long.

What a batch shares, the tags list, the global count and every article's details among them, is read from
Postgres within that one execution, for requests that were all waiting when it was sent. Nothing outlives it.

## Writes

Writes are committed in groups. A free writer queues the statements of every waiting write into one pipeline,
which Postgres runs as one implicit transaction with one commit, and each response waits for that commit. When
Postgres rejects a statement the group has rolled back, so each of its writes runs again alone. Lookups and
ownership checks are CTEs of the write itself (`404`/`403` come from the row it returns).

## Scheduling

At startup every thread of the process moves to `SCHED_BATCH` (no privileges needed, later threads inherit
it). The server's threads wake up constantly, and under `SCHED_BATCH` those wakeups don't preempt a busy
Postgres backend.

Postgres sessions run with `plan_cache_mode = force_generic_plan`, `jit = off`,
`max_parallel_workers_per_gather = 0` and `enable_memoize = off`. Every statement is prepared once per connection.

## bcrypt

[`bcrypt4`](bcrypt4) computes four bcrypt hashes at once. Blowfish waits on dependent S-box loads, so four
independent lanes interleaved in one loop run about 3.3× the throughput of `x/crypto/bcrypt` (20 ms vs 67 ms per
hash at cost 10). Its output is identical (tested against `x/crypto/bcrypt`). Three workers gather up to four
hashes for at most 50 ms, which also keeps hashing from taking over the cores requests need. A hash that waited
over 5 s is answered with `503` instead of being computed for a client that has likely given up.

## Tuning

| Variable | Default | |
|---|---|---|
| `DB_READERS` | 8 | connections for the articles statement |
| `DB_FAST` | 2 | connections for the cheap reads |
| `DB_WRITERS` | 4 | group-commit connections |
| `DB_GAP_US` | 10000 | minimum gap between articles statement batches |
| `LOOPS` | cores | epoll loops |
| `BCRYPT_WORKERS` / `BCRYPT_WAIT_MS` | 3 / 50 | bcrypt groups in flight / how long a group waits to fill |
| `BCRYPT_SHED_MS` | 5000 | how long a hash may wait before it is refused, 0 never |
| `SCHED_BATCH` | 1 | 0 keeps the default scheduling policy |
| `GOGC_PERCENT` / `MEMORY_LIMIT_MB` | 400 / 4096 | GC |
