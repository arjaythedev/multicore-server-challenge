# rust-epoll-theCatWisel

Front: direct

HTTP/1.1 backend written in Rust on top of Linux epoll (`SO_REUSEPORT`) and a custom binary PostgreSQL v3 wire client. Everything in the binary (Linux syscall FFI, HTTP parsing, JSON codec, Base64/Base64URL, SHA-NI / scalar SHA-256, HMAC-SHA256, and multi-lane EksBlowfish bcrypt) is implemented in-tree with zero external crate dependencies (`std` only).

## Design

Four `SO_REUSEPORT` reactor threads run under `SCHED_BATCH`, isolate their kernel file descriptor tables via `unshare(CLONE_FILES)` (bypassing `files_struct` lock contention and `fget_light` atomic refcounting while giving each reactor its own `RLIMIT_NOFILE` table), probe `getrlimit(RLIMIT_NOFILE)` at startup to bound an intrusive $O(1)$ Idle-LRU keep-alive connection pool, and parse HTTP/1.1 requests directly out of a thread-local 256 KiB read buffer whenever a request arrives in one read. Responses are written back with `writev`.

Database work is split across `cores.max(4)` read workers (8 on an 8-core host) and `1` write worker, each holding a single persistent PostgreSQL connection with prepared statements in binary wire format and session-level planner tuning (`plan_cache_mode = force_generic_plan`, `jit = off`, `max_parallel_workers_per_gather = 0`, `work_mem = 32MB`, `random_page_cost = 1.1`, `effective_io_concurrency = 200`):

- Read workers gather batches via a wakeup-suppressed age-bounded queue (`take_aged`) driven by `EWMA_BATCH_LEN`, `EWMA_BATCH_US`, and `BUSY_READ_WORKERS` (using a short single-hash coalescing horizon while idle read workers are available and widening to a Little's Law window when all read workers are busy), and skip requests whose client socket closed while queued via lock-free slot epochs. Each batch executes over reusable byte arenas and reusable `ArrayEncoder` buffers. Phase A is split into two `Sync` sub-pipelines sent in a single `flush()`: Sub-pipeline A1 (`tags`, `uid`, `uemail`) drains first so `GET /api/tags`, `GET /api/user`, and login lookups dispatch immediately to reactor/crypto workers while PostgreSQL executes Sub-pipeline A2 (`prof`, `aslug`, `aid`, `cmts`, `global`, `tag`, `author`, `favlist`, `feed`). Point-lookup queries (`uid`, `uemail`, `prof`, `aslug`, `aid`) and Phase B queries (`artmeta`, `artau`) use PostgreSQL 18 B-Tree ScalarArrayOp (`WHERE col = ANY($1)`) scans so `_bt_preprocess_array_keys` sorts and walks index pages in ascending key order in a single scan and ReadWorker maps rows back to `KeySet` ordinals in $O(1)$ in Rust. List queries (`global`, `tag`, `author`, `favlist`) project `(slug, title, description, created_at, updated_at)` in Phase A (`MetaSource::PhaseA`), while `feed` page queries project `(k, id, author_id)` as index-only scans on `articles_author_idx (author_id, id DESC)` and fetch their metadata once per unique article in Phase B (`artmeta`, without `body`). Comment rows (`cmts`) return `author_id` in Phase A2 and deduplicate comment author profile lookups into Phase B's `artau` array scan alongside article authors. Phase A also collapses overlapping global article pages (`lim + off <= 200`) into a single B-Tree window scan (`global_win`), materializes prolific-author floor cutoffs and oldest-page 1,000-article checks (`ORDER BY a.id ASC LIMIT 1 OFFSET 999`) across up to 32 shared hub authors on `feed`, and caps `articlesCount` at 1,000. Phase B fetches tags and favorite counts once per unique article via `artx`, resolves author profiles once per unique author (`artau`), and evaluates per-viewer `favorited` and `following` flags via grouped primary-key array lookups (`flags`) with 64-bit viewer bloom masks. Viewer-independent JSON fragments are formatted once into a batch-local byte buffer and unflagged responses within the batch share a single `Arc<[u8]>` payload.
- Write workers execute each batch of mutations inside a single Extended Query Protocol implicit pipeline transaction (committing at `Sync`), grouping concurrent favorite, follow, and comment creation (`newcmt_batch`) operations into `unnest` statements with per-table/per-slug conflict scoping and falling back to per-item execution if a statement fails. Article creation (`newart`) completes directly in the write worker in one round trip, while post-commit favorite and update reads pass `known_fav` to the read queue so Phase B skips redundant `favorites_pkey` lookups.
- Crypto worker threads (`(cores / 2).max(3)`) verify and hash passwords in multi-way word-sliced lockstep (`bcrypt_lanes<N>` over 64-byte cache-line aligned 4,224-byte `BfState` lanes so S-boxes never 4K-alias in L1D cache). On x86-64 CPUs with BMI1/BMI2, `build.rs` generates register-resident multi-lane `bc_expand0` assembly kernels (`shrx`, `ah`, and `bextr` extraction styles across widths `1..=6`, inspired by `@nick-potts`'s `asm_gen` in `zig-iouring-nick-potts` and `@WorriedArrow`), keeping up to 5 lanes (`10` Blowfish halves) in general-purpose registers with single-register displacement addressing. Startup calibration benchmarks all kernels and lane widths against the host CPU's L1D cache and register file, and coalesces full `N`-lane batches via `EWMA_BCRYPT_US` and `EWMA_CRYPTO_LEN`. JWT verification reuses precomputed SHA-256 `ipad`/`opad` midstates for the server secret.
