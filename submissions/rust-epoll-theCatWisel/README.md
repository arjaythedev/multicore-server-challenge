# rust-epoll-theCatWisel

Front: direct

HTTP/1.1 backend written in Rust on top of Linux epoll (`SO_REUSEPORT`) and a custom binary PostgreSQL v3 wire client. Everything in the binary (Linux syscall FFI, AVX2 HTTP header scanning and JSON escaping, `PCLMULQDQ` Gzip CRC-32 and Deflate fixed-Huffman compression, Base64/Base64URL, SHA-NI / scalar SHA-256, HMAC-SHA256, and multi-lane EksBlowfish bcrypt) is implemented in-tree with zero external crate dependencies (`std` only).

## Design

Four `SO_REUSEPORT` reactor threads run under `SCHED_BATCH` at `nice 5` (`setpriority`), isolate their kernel file descriptor tables via `unshare(CLONE_FILES)` (bypassing `files_struct` lock contention and `fget_light` atomic refcounting while giving each reactor its own `RLIMIT_NOFILE` table), probe `getrlimit(RLIMIT_NOFILE)` at startup to bound an intrusive $O(1)$ Idle-LRU keep-alive connection pool with bitfield-packed 72-byte `ClientSlot` states and `MADV_HUGEPAGE`-backed arenas, and parse HTTP/1.1 requests directly out of a thread-local 256 KiB read buffer whenever a request arrives in one read. Header scanning, JSON string parsing, and JSON string escaping use 32-byte AVX2 vector lanes (`find_byte`, `scan_clean_avx2`, `write_str`), Base64URL token decoding uses SSSE3 `pshufb`/`pmaddubsw`/`pmaddwd` vector lanes, and batch-shared responses `>= 512` bytes for clients advertising `Accept-Encoding: gzip` are compressed via a 2-way L1D `CRC32C` (`_mm_crc32_u32`) `hash4` LZ77 matcher with 32-byte AVX2 match-length comparison, a 64 KiB `FIXED_PAIR` 2-byte Deflate fixed-Huffman lookup table, and 4-lane 64-byte `VPCLMULQDQ`/`PCLMULQDQ` carry-less multiplication with Barrett reduction for IEEE 802.3 CRC-32 before being written back with `writev`.

Database work is split across `cores.max(4)` read workers (8 on an 8-core host) and `(cores / 2).max(2)` write workers (4 on an 8-core host), each holding a persistent PostgreSQL connection (`TCP_NODELAY` + `TCP_QUICKACK`) with zero-copy in-place `PipelineBuf` frame parsing, hardware SSE4.2 `CRC32C` hash tables (`HwBuildHasher`), prepared statements in binary wire format, and session-level planner tuning (`plan_cache_mode = force_generic_plan`, `jit = off`, `max_parallel_workers_per_gather = 0`, `work_mem = 32MB`, `random_page_cost = 1.1`, `cpu_index_tuple_cost = 0.0005`, `effective_io_concurrency = 200`):

- Read requests are partitioned into three dedicated lanes (`LANE_FAST` for tags/users/profiles/slugs/global/filtered lists, `LANE_CMTS` for comments, and `LANE_FEED` for feeds) with a bounded active concurrency cap (`(rw.saturating_sub(1)).max(3)`, i.e. 7 active connections on an 8-core host) and per-lane caps (`3 / 2 / 2`) with work-conserving and oldest-first `+1` slot borrowing. Each queue tracks the exact arrival `Instant` of its head item across partial drains (`Timestamped`), coalesces batches outside the dispatcher lock via per-lane EWMA latency (`EWMA_LANE_US`) and batch size (`EWMA_LANE_LEN`), and drops closed client sockets before touching PostgreSQL.
- Phase A is split into two `Sync` sub-pipelines sent in a single `flush()`: Sub-pipeline A1 (`tags`, `uid`, `uemail`, `prof`) drains first so `GET /api/tags`, `GET /api/user`, `GET /api/profiles/:username` (resolving viewer `following` status inline via `EXISTS`), and login lookups dispatch immediately to reactor/crypto workers while PostgreSQL executes Sub-pipeline A2 (`aslug`, `aid`, `cmts`, `global`, `tag`, `author`, `favlist`, `feed`). Every batch that serves `GET /api/tags` or touches articles queries `SELECT id, name FROM tags` from PostgreSQL for that batch (`st_tags` in Sub-pipeline A1 or `b_tags` in Phase B) and resolves tag slices directly from the batch `PipelineBuf` (`Vec<Cell>`) with zero cross-batch state.
- Comment threads (`cmts` on `LANE_CMTS`) execute in a single PostgreSQL round trip in Sub-pipeline A2, returning comment rows (`Kind 0`), distinct comment author profiles (`Kind 1`), and thread-scoped viewer follow hits (`Kind 2` via `rv(v, k)` and `EXISTS` against `follows_pkey`) so `LANE_CMTS` completes with zero Phase B round trip.
- Point-lookup queries (`uid`, `uemail`, `aslug`, `aid`) and Phase B queries (`artmeta`, `artau`) use PostgreSQL 18 B-Tree ScalarArrayOp (`WHERE col = ANY($1)`) scans, and Phase B sorts `meta_req_ids`, `sorted_arts`, and `sorted_authors` in ascending ID order before binding `artmeta`, `artx`, and `artau` so correlated subqueries on `article_tags_pkey` and `favorites_article_idx` walk B-Tree leaf pages monotonically. List queries (`global`, `tag`, `author`, `favlist`) project `(slug, title, description, created_at, updated_at)` in Phase A (`MetaSource::PhaseA`), while `feed` page queries project `(k, id, author_id)` as index-only scans on `articles_author_idx (author_id, id DESC)` and fetch their metadata once per unique article in Phase B (`artmeta`, without `body`). Phase A also collapses overlapping global article pages (`lim + off <= 200`) into a single B-Tree window scan (`global_win`), materializes prolific-author floor cutoffs and oldest-page 1,000-article checks (`ORDER BY a.id ASC LIMIT 1 OFFSET 999`) across up to 32 shared hub authors on `feed`, and caps `articlesCount` at 1,000. Phase B fetches tags and favorite counts once per unique article via `artx`, resolves author profiles once per unique author (`artau`), and evaluates per-viewer `favorited` and `following` flags via grouped primary-key array lookups (`flags`) with 64-bit viewer bloom masks. Viewer-independent JSON fragments are formatted once into a batch-local byte buffer and unflagged responses within the batch share a single `Arc<[u8]>` payload.
- Write workers execute each batch of mutations inside a single Extended Query Protocol implicit pipeline transaction (committing at `Sync`), grouping concurrent favorite (`fav_batch` ordered by `(aid, uid)` for heap-page locality), follow (`follow_batch`), and comment creation (`newcmt_batch` ordered by `(aid, cid)`) operations into `unnest` statements with per-table/per-slug conflict scoping and falling back to per-item execution if a statement fails. Article creation (`newart`) completes directly in the write worker in one round trip, while post-commit favorite and update reads enqueue `ArticleById` into `LANE_FAST` (`push_batch`).
- Crypto worker threads (`(cores / 2).max(3)`) verify and hash passwords in multi-way word-sliced lockstep (`bcrypt_lanes<N>` over 64-byte cache-line aligned 4,224-byte `BfState` lanes so S-boxes never 4K-alias in L1D cache), pairing 1 normal-priority (`SCHED_BATCH` `nice 0`) primary worker with `crypto_workers - 1` `nice 10` secondary workers and overlap-aware full-width batch coalescing so `bcrypt` yields politely to active PostgreSQL queries without starving under 100% CPU saturation. On x86-64 CPUs with BMI1/BMI2, `build.rs` generates full-loop fused multi-lane `bc_cost10` assembly kernels (`shrx`/`rorx`, `ah`, and `bextr` extraction styles across widths `1..=6`), executing initial salted key expansion, all `2^10` key/salt expansion rounds with 128-bit SSE2 `pxor` `P`-array mixing, and all `64 × 3` final `OrpheanBeholderScryDoubt` ECB block encryptions in a single FFI call while keeping all 6 lanes (`12` Blowfish halves) in general-purpose registers (`shrx`/`rorx`) with zero stack spills. Startup calibration benchmarks all kernels and lane widths against the host CPU's L1D cache and register file. JWT verification reuses precomputed SHA-256 `ipad`/`opad` midstates with cached `SHA-NI` + SSSE3 `pshufb` dispatch, vDSO `CLOCK_REALTIME_COARSE` expiry checks, and 256-bit AVX2 `vpxor` + `vptest` (`ct_eq_32`) tag comparison.
