# C: miserable submission

Front: direct

god fucking damn it i paid for the whole CPU and i'm gonna USE the whole CPU

anyways long story short i went insane making this :) when i started i only had scooter1337 as my competition, but eventually others started showing up and i had to keep on frying the same fuckass codebase.

moving on, here are the very cool tricks i've used:

- workers, each with its own `SO_REUSEPORT` listener, so the kernel load-balances the accepts. each worker has its own event loop and conn set; the ONLY cross-worker coordination is the shared read queue further down. the default is adaptive: `clamp(cores/2, 2, 4)`, since bigger read batches (see below) cost less Postgres work than many small ones.
- everything lives in one epoll set. client sockets, listening sockets and every libpq connection of a worker sit in the same epoll. there is no "database thread", so nobody is ever waiting on a queue while another thread is idle. handlers are state machines over libpq's async API: a bcrypt login is ~60-100 ms of pure CPU and a slow client write can take forever, none of it blocks anybody else, it just suspends and resumes on the next epoll event. this is the structurally impossible version of the worker-starvation bug that determines the usual C submission score. the one exception is the offload pool (bcrypt + json rendering), which posts its answers back to the owning epoll through a per-worker mailbox so a batch of renders never stalls accepts.
- one process-wide shared read queue, and every list-shaped read (all / tag / author / favorited / feed) is ONE prepared statement now. reads of every kind from every worker join the same queue, the first free read conn of any worker takes up to `READ_BATCH` (512) as one execution, and the statement branches per request row so all five kinds ride the same queue slot and the same execution. `LIST_ONE` computes pages, capped counts, tags and author rows once per distinct article/key, one `artx` enrichment pass covers the union of all kinds' article ids (one page of `?tag=` + one page of `?author=` in the same window enriches each article once, not twice), and the rows come back with the request ordinal for demux. the answer is parked in the submitting worker's inbox and resumes on its own epoll loop; a batch result is shared out by refcount (a busy worker's conn can drain another worker's queue, e.g. while its own is stuck in a write group), the last holder clears the `PGresult`, and the batch is thrown away right after the callbacks run. this is within-statement work, i don't think this was against the rules.
- tuple parsing + json rendering happen OFF the io threads, as jobs on the offload pool. turning 512 rows into a response is the biggest per-response CPU cost and doing it on the loop delays everyone else's accepts. request refcounts are atomic, so a client disconnecting mid-render can never free the request out from under the pool thread, and the finished response marshals back to the conn's loop through the mailbox and gets written there. a render that chains another pg op (login -> register, update -> re-read) posts the submit back home first, because libpq conns are only ever touched by their own pool's thread.
- write group commit, also quite cancer to implement without abstractions. all writes of a worker go onto one write lane. a lone write waits up to `WRITE_WINDOW_MS` (5 ms) for friends; a queue of `WRITE_IMMEDIATE` (4) or more leaves immediately. the lane pipelines up to `WRITE_GROUP` (32) prepared writes and closes with a single `PQpipelineSync`, so one durable commit serves the whole group. every response still waits for that commit, obviously.
- one statement per request, including the ones that have to return a row. the per-request "does the user still exist" read is gone (the jwt says who you are; viewer-keyed statements return zero rows for a deleted user and the routes map that to 401). favorite add/remove return the full article from the write itself, the count is the pre-write snapshot +/- the row the CTE actually inserted/deleted because same-snapshot CTEs can't see their own write. article update returns the new row via `RETURNING` and tells "not the author" apart by a NULL from the `LEFT JOIN`ed update. login renders from the row it already fetched for the bcrypt hash instead of re-reading the user. those read-backs used to be a second visit to the read-batching queue, i.e. a whole extra round trip plus up to `READ_WINDOW_MS` of latency each.
- responses are one `writev`: header block hand-built into a small stack buffer (no `vsnprintf` pass over the body, no `Content-Length` re-scan) + body iovec straight out of the response buf, zero copies. `conn_respond_move` hands the buffer over so the write path owns it until the last byte flushes.
- timestamps come back from postgres as int8 epoch microseconds and are formatted in C. `to_char` per row was doing locale-ish string work for every timestamp of every row, and the float64 route (`extract(epoch)`) loses sub-microsecond precision on dates far from 1970; the C side does exact civil-date decomposition into `YYYY-MM-DDTHH:MM:SS.mmmmmmZ`. verified against `to_char` over 20k rows, zero mismatches.
- postgres conns heal themselves. a dead conn gets reconnected from the pool tick with 100 ms -> 5 s exponential backoff, fully non-blocking (`PQconnectStart` / `PQconnectPoll` on the same epoll set, session `SET`s, then all `PQprepare`s pipelined into one round trip). work already sitting on the dead conn still fails fast; new work keeps hitting the survivors and then the healed lane. before this, `podman restart postgres` was a permanent 500 machine.
- one-shot HMAC on the jwt verify path instead of a fresh hash each request, and idle keep-alive at 70 s so it outlives Nginx's 60 s upstream idle (and, in direct mode, bounds the memory of idle browser connections).

honorable mention to bullshit that didn't meet the list: `TCP_NODELAY` on client sockets (coalescing hurts interactive p99 and the responses are single writes anyway), two-buffer request arenas, and one allocation per response write.

## stuff you can change

- `WORKERS` (default 2-4, adaptive), `READ_BATCH` (512), `READ_WINDOW_MS` (0), `WRITE_GROUP` (32), `WRITE_WINDOW_MS` (5), `CRYPTO_THREADS` (one per core).
- do please tune this, as these are the numbers i actually used for testing 50k locally and are DEFINITELY fucked on a real server.
